# کاربران، نقش‌ها و دسترسی‌ها (RBAC)

این سند توضیح می‌دهد دسترسی‌ها چطور کار می‌کنند، یک قابلیت جدید (مثلاً بخش تازه‌ای از پنل ایزابل) چطور اضافه می‌شود، و قبل از تحویل نسخهٔ جدید چه چیزهایی باید بررسی شود.

## ۱. مفاهیم

| مفهوم | توضیح |
|---|---|
| **Feature (قابلیت)** | هر کاری که می‌شود به کسی اجازه داد یا نداد. کلید آن به شکل `feature.action` است (مثل `outages.view`). همه در [`features.py`](../features.py) ثبت می‌شوند و منو و فرم دسترسی‌ها از روی همین فهرست ساخته می‌شوند. |
| **Role (نقش)** | مجموعه‌ای از کلیدها. هر کاربر یک نقش دارد. نقش‌ها را در «پنل ← نقش‌ها و دسترسی‌ها» می‌سازید، کپی می‌کنید و ویرایش می‌کنید. |
| **Override (استثنا)** | برای یک کاربر خاص: «اضافه» (grant) یک دسترسی بیشتر از نقش، «محدود» (deny) یک دسترسی کمتر از نقش. **deny همیشه برنده است.** |
| **مدیر ارشد (Super Admin)** | نقش سیستمی که همیشه همه‌چیز را دارد، حتی قابلیت‌هایی که بعداً اضافه می‌شوند. قابل ویرایش یا حذف نیست. |

ترتیب تصمیم `user_can(user, key)` (در `app.py`):

1. کاربر وارد نشده، غیرفعال یا بدون نقش ← **ندارد**
2. کلید در `features.py` ثبت نشده ← **ندارد** (جلوی غلط تایپی را می‌گیرد)
3. نقش مدیر ارشد ← **دارد**
4. وگرنه: (دسترسی‌های نقش ∪ اضافه‌ها) − محدودها

نتیجه برای هر درخواست یک بار حساب و کش می‌شود؛ هر تغییری که مدیر می‌دهد از **درخواست بعدی** کاربر اعمال می‌شود (بدون ری‌استارت).

**بررسی همیشه سمت سرور است.** مخفی‌شدن دکمه فقط برای راحتی است؛ اگر کسی آدرس را مستقیم باز کند صفحهٔ «دسترسی ندارید» (403) یا برای API پاسخ JSON با کد 403 می‌گیرد.

### حفاظت‌ها

- آخرین مدیر ارشدِ فعال قابل حذف، غیرفعال‌کردن یا تنزل نیست.
- هیچ‌کس نقش، وضعیت یا دسترسی‌های حساب خودش را عوض نمی‌کند و خودش را حذف نمی‌کند (خودقفلی ممکن نیست).
- هیچ‌کس دسترسی‌ای را که خودش ندارد به دیگری یا به نقشی نمی‌دهد؛ فقط مدیر ارشد حساب مدیر ارشد می‌سازد یا تغییر می‌دهد.
- نقش سیستمی حذف نمی‌شود؛ نقشی که کاربر دارد هم حذف نمی‌شود.
- هر تغییر کاربر، نقش یا دسترسی در «لاگ فعالیت‌ها» ثبت می‌شود (چه کسی، چه چیزی، قبل ← بعد؛ هرگز رمز).
- **قفل موقت حساب:** بعد از `LOGIN_LOCK_ATTEMPTS` رمز اشتباه برای یک نام کاربری در `LOGIN_LOCK_MINUTES` دقیقه، آن نام کاربری به همین مدت قفل می‌شود (از هر IP). مدیر می‌تواند از صفحهٔ کاربران «باز کردن قفل» بزند؛ ریست رمز هم قفل را باز می‌کند. این شمارنده در حافظهٔ همان یک پردازش است و با ری‌استارت پاک می‌شود.
- **خروج اجباری:** کاربری که غیرفعال شود در اولین درخواست بعدی‌اش از سامانه خارج می‌شود.
- **گزارش دسترسی‌ها:** در صفحهٔ کاربران دکمهٔ «گزارش دسترسی‌ها (CSV)» یک ردیف برای هر کاربر و یک ستون برای هر کلید می‌دهد. مقدار خانه‌ها: `role` (از نقش)، `grant` (اضافه)، `deny` (محدود شده)، `super` (مدیر ارشد)، خالی (ندارد).

## ۳. افزودن قابلیت جدید (قرارداد)

مثال: صفحهٔ «صندوق صوتی» از ایزابل، فقط برای دیدن، و یک دکمهٔ حساس برای پاک‌کردن پیام‌ها.

### گام ۱ — یک خط در `features.py` برای هر کار

```python
register_feature('voicemail.view', 'مشاهده‌ی صندوق صوتی', MONITOR, 'پیام‌های صوتی داخلی‌ها',
                 menu_item=MenuItem('voicemail_list', 'phone', 'voicemail', 'صندوق صوتی', 30))
register_feature('voicemail.delete', 'حذف پیام صوتی', MONITOR, dangerous=True)
```

- `group` یکی از `GROUPS` است (`دفترچه`، `پایش`، `سیستم`)؛ گروه تازه را اول به `GROUPS` اضافه کنید.
- `menu_item` اختیاری است: `MenuItem(endpoint, icon, nav, label, order)`. `icon` از `templates/_icons.html` و `nav` همان مقداری است که صفحه در `{% set nav = '...' %}` می‌گذارد.
- اشتباه (کلید تکراری، فرمت غلط، گروه ناشناخته، منو به endpoint ناموجود) باعث می‌شود برنامه **اصلاً بالا نیاید** و پیام خطای واضح بدهد.

### گام ۲ — روت با `@require_permission`

```python
    @app.route(f'/{admin_prefix}/voicemail')
    @require_permission('voicemail.view')
    def voicemail_list():
        return render_template('voicemail.html', messages=...)

    @app.route(f'/{admin_prefix}/voicemail/<int:message_id>/delete', methods=['POST'])
    @require_permission('voicemail.delete')
    def voicemail_delete(message_id):
        ...
        log_activity('deleted', 'voicemail', ...)
```

هر روت **باید** یکی از این سه را داشته باشد، وگرنه تست قرارداد شکست می‌خورد:
`@require_permission('key')` (بیشتر روت‌ها)، `@login_only` (هر کاربر واردشده، مثل تغییر رمز خود)، `@public_endpoint` (عمومی، عمداً).

### گام ۳ — نمایش در تمپلیت با `can()`

```jinja
{% extends 'base.html' %}
{% set shell = 'admin' %}{% set nav = 'voicemail' %}
...
{% if can('voicemail.delete') %}
<form action="{{ url_for('voicemail_delete', message_id=m.id) }}" method="post" data-confirm="{{ t('این پیام حذف شود؟') }}">
  <input type="hidden" name="csrf_token" value="{{ (csrf_token())|e }}">
  <button class="btn btn-sm btn-outline-danger">{{ t('حذف') }}</button>
</form>
{% endif %}
```

منو خودش آیتم را نشان می‌دهد؛ چیزی در `base.html` لازم نیست. متن‌های فارسی جدید را در `i18n.py` ترجمه کنید (تست `test_i18n` جای خالی را نشان می‌دهد).

### گام ۴ — تست

در [`tests/test_rbac_routes.py`](../tests/test_rbac_routes.py):

```python
PERMISSIONS = {
    ...
    'voicemail_list': 'voicemail.view', 'voicemail_delete': 'voicemail.delete',
}

def requests_to_check(a):
    return [
        ...
        ('GET', f'/{a}/voicemail'), ('POST', f'/{a}/voicemail/{MISSING}/delete'),
    ]
```

با همین دو خط، تست‌ها برای هر سه نقش پیش‌فرض بررسی می‌کنند که مجاز 200 (یا هر چیزی جز 403) و غیرمجاز 403 بگیرد. تست‌های قرارداد هم این‌ها را تضمین می‌کنند:

- هر روت تصمیم دسترسی دارد؛ فهرست روت‌های عمومی و «فقط ورود» صریح است.
- هر کلیدِ روت‌ها در `features.py` ثبت است و **هر Feature دست‌کم یک روت محافظت‌شده دارد**.
- جدول بخش ۲ همین سند با `features.py` یکی است.

### گام ۵ — دادن دسترسی

مدیر ارشد خودکار آن را دارد. برای بقیه در «نقش‌ها و دسترسی‌ها» تیک بزنید (نقش‌های موجود خودکار کلید جدید نمی‌گیرند؛ این عمدی است). اگر می‌خواهید نقش پیش‌فرض در **نصب تازه** هم آن را داشته باشد، کلید را به `SYSTEM_ROLES` در `features.py` و جدول بخش ۲ اضافه کنید.

## ۴. چک‌لیست تحویل

اجرا روی سرور ویندوز با NSSM و Waitress و **فقط یک پردازش** (thread همگام‌سازی PBX و شمارنده‌های قفل ورود داخل همان پردازش‌اند).

1. **بک‌آپ:** `nssm stop HotelExtensions` و یک کپی از `C:\HotelExtensions\hotel_extensions.db` جای امن بگذارید.
2. **آزمایش مهاجرت روی کپی دیتابیس واقعی** (فایل اصلی فقط خوانده می‌شود):
   ```powershell
   cd C:\NewRelease
   C:\HotelExtensions\.venv\Scripts\python.exe tools\check_rbac_migration.py C:\HotelExtensions\hotel_extensions.db
   ```
   باید `RESULT: OK` بدهد، همهٔ کاربران فعلی `super_admin` باشند و تعداد ردیف‌های داخلی‌ها/بخش‌ها تغییر نکرده باشد.
3. **به‌روزرسانی سرویس:**
   ```powershell
   nssm stop HotelExtensions
   robocopy C:\NewRelease C:\HotelExtensions /E /XD .git .venv venv __pycache__ tmp_imports backups logs /XF hotel_extensions.db .env .secret_key .admin_prefix
   cd C:\HotelExtensions
   .\.venv\Scripts\pip install -r requirements.txt
   nssm start HotelExtensions
   ```
   در اولین اجرا برنامه خودش قبل از مهاجرت یک بک‌آپ در `C:\HotelExtensions\backups\hotel_extensions_pre_rbac_<زمان>.db` می‌سازد. اگر ساخت بک‌آپ شکست بخورد، برنامه بالا نمی‌آید و چیزی تغییر نمی‌کند (`logs\service.log` را ببینید).
4. **ورود با هر نقش:** با حساب مدیر وارد شوید، یک کاربر آزمایشی «اپراتور» و یک «مشاهده‌گر» بسازید و با هر کدام وارد شوید: منو فقط بخش‌های مجاز را نشان دهد.
5. **تست 403:** با کاربر مشاهده‌گر آدرس `/<پیشوند>/backup` را مستقیم باز کنید ← صفحهٔ «دسترسی ندارید».
6. **قفل موقت:** با کاربر آزمایشی ۵ بار رمز اشتباه بزنید ← پیام قفل؛ از صفحهٔ کاربران «باز کردن قفل».
7. **نقش واقعی همه:** نقش هر کاربر را تنظیم کنید و کاربرهای آزمایشی را حذف کنید. «گزارش دسترسی‌ها (CSV)» را برای سابقه نگه دارید.
8. **Rollback** (اگر لازم شد):
   - **فقط کد:** `nssm stop HotelExtensions`، فایل‌های نسخهٔ قبل را برگردانید، `nssm start HotelExtensions`. نسخهٔ قبل با دیتابیس جدید کار می‌کند (فقط جدول و ستون اضافه شده) ولی دوباره همهٔ کاربران واردشده به همه‌چیز دسترسی دارند.
   - **کامل:** `nssm stop HotelExtensions`، فایل `backups\hotel_extensions_pre_rbac_*.db` را جای `hotel_extensions.db` بگذارید، نسخهٔ قبل کد را برگردانید، `nssm start HotelExtensions`. تغییراتی که بعد از مهاجرت ثبت شده از بین می‌رود.

## ۵. تنظیمات

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `LOGIN_LOCK_ATTEMPTS` | `5` | چند رمز اشتباه برای یک نام کاربری تا قفل موقت؛ `0` = خاموش |
| `LOGIN_LOCK_MINUTES` | `15` | مدت قفل و بازهٔ شمارش تلاش‌ها (دقیقه) |
